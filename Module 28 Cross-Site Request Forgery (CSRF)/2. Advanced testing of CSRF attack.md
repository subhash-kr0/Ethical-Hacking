# Advanced Testing of CSRF (Cross-Site Request Forgery) Attacks

CSRF (Cross-Site Request Forgery) attacks exploit the trust a web application has in the browser of an authenticated user. By tricking the victim into performing unintended actions on the application, attackers can cause state-changing operations such as modifying user details, transferring funds, or even deleting resources.

---

## 1. Understanding the Workflow of CSRF
1. The attacker crafts a malicious link or embeds a forged request (e.g., via `<form>` or JavaScript).
2. The victim, while authenticated in the target application, interacts with the malicious payload.
3. The browser sends the request to the target application, leveraging the victim’s credentials (e.g., session cookies).
4. The server processes the request, believing it to originate from the legitimate user.

---

## 2. Advanced Testing Techniques

### **2.1 Analyze Application Behavior**
- **Identify State-Changing Actions**: Determine endpoints that modify data (e.g., `/update-profile`, `/transfer-funds`).
- **Inspect Requests**: Use tools like Burp Suite, OWASP ZAP, or browser developer tools to examine:
  - HTTP methods (`POST`, `PUT`, etc.).
  - Headers, cookies, and tokens associated with requests.
  - The presence or absence of CSRF protection mechanisms.

### **2.2 Bypass CSRF Protections**
#### **2.2.1 Missing or Weak CSRF Tokens**
- **Test for Token Absence**: Remove the `csrf_token` parameter and check if the request still succeeds.
- **Replay Token**: Use the same token multiple times to identify if it is single-use or static.
- **Predict Tokens**: Analyze the token format and test for predictable patterns or static values.

#### **2.2.2 CSRF Protection via Referer/Origin Headers**
- **Spoof Referer/Origin**: Use tools like Burp Repeater or custom scripts to spoof headers.
- **Test Missing Headers**: Remove the `Referer` or `Origin` headers and observe the application’s behavior.

#### **2.2.3 SameSite Cookies**
- **Test on Different Browsers**: Verify cookie behavior in older browsers that do not enforce `SameSite` attributes.
- **Check GET Requests**: Analyze if sensitive actions use `GET` methods, as `SameSite` does not fully protect them in some cases.

### **2.3 Exploit CSRF Vulnerabilities**
1. **Craft Malicious Payloads**:
   - Use an HTML `<form>` with hidden inputs.
   - Create JavaScript payloads for automated execution.
2. **Host Payload**:
   - Use platforms like Pastebin or a custom server to host the payload.
3. **Trick the Victim**:
   - Deliver the payload via email, phishing websites, or embedded in third-party content.

## 3. Example Attack Scenarios

### **3.1 Exploiting a Bank Transfer Endpoint**
1. Identify the vulnerable endpoint: `/transfer`.
2. Craft a payload:
   ```html
   <form action="https://vulnerable-bank.com/transfer" method="POST">
       <input type="hidden" name="account" value="attacker_account">
       <input type="hidden" name="amount" value="10000">
       <input type="submit" value="Click me!">
   </form>
  ```
3. Host and deliver the form to the victim.

## 3.2 Exploiting User Profile Updates
1. Intercept a POST request for updating user details.
2. Craft the payload:
```html
<img src="https://vulnerable-site.com/update-profile?email=attacker@example.com" style="display:none;">
```
3. Embed the payload in an email or malicious website.

## 4. Mitigation Testing Checklist
- Ensure all state-changing actions require CSRF tokens.
- Verify tokens are unique, unpredictable, and tied to the user session.
- Enforce SameSite and HttpOnly attributes on cookies.
- Validate Referer or Origin headers on sensitive requests.
- Avoid using GET for state-changing actions.

## 5. Tools for Advanced CSRF Testing
- Burp Suite: For intercepting and modifying requests.
- OWASP ZAP: For automated vulnerability scanning.
- Postman: For manually testing API requests.
- Browser Developer Tools: For quick inspection of request payloads.
